Считывает формат файла перегонного куба (в настоящее время HDF5 на основе версии 1.1) и выводит скомпилированные данные кадра в FIFO для кодера. TODO: В Alembic 1.5 представлен новый формат данных, который должен значительно улучшить скорость чтения.

Поддерживаемые функции перегонного куба

Мы поддерживаем static и динамические преобразования с static или однородными полисетками в качестве листьев. Гетерогенные сетки (с меняющейся топологией) на данный момент не поддерживаются, так как не подходят для нашей схемы сжатия.

Генерация кадров

Alembic поддерживает разное расстояние между кадрами для каждого объекта в дереве сцены. Например. сетка может иметь кадры через нерегулярные интервалы, а преобразование вместо этого имеет фиксированный временной шаг 1/30 с в том же файле. Кэш геометрии CryEngine не поддерживает это. Каждый кадр содержит данные обо всех объектах сцены, что упрощает декодирование в реальном времени. Чтобы добиться этого, компилятор перегонного куба сначала создает расширенный набор всех времен кадра объектов сцены ( AlembicCompiler::CheckTimeSampling). Для каждого уникального найденного времени кадра будет выведен кадр.

Разделение вершин

Alembic имеет отдельные массивы для каждого элемента данных вершины. Это, например, позволяет двум треугольникам использовать одни и те же данные о положении вершины, но не использовать общие координаты текстуры. Графические процессоры поддерживают только один индексный буфер для всех элементов, поэтому в этом случае нам необходимо также дублировать данные о позиции. Это справедливо даже в том случае, если UV-развертки будут различаться только в одном кадре всей анимации, потому что нам нужно, чтобы топология оставалась одинаковой для всех кадров.

Чтобы добиться этого, мы сначала вычисляем 64-битный хэш для каждой вершины по всем кадрам анимации сетки (AlembicCompiler::ComputeVertexHashes). Если хэш вершины различен для двух треугольников, его необходимо разделить. Обратите внимание, что существует вероятность коллизии хэшей, но это маловероятно при 64 битах. Проверка коллизий будет довольно медленной, поэтому в данный момент мы этого не делаем.

Гладкая нормальная генерация

Если сетка не содержит нормалей, нам нужно вычислить гладкие нормали для сетки в этих случаях (AlembicCompiler::CalculateSmoothNormals). Мы не могли удалить вспомогательные сетки без нормалей, потому что Maya не хранит никакой информации о нормалях для сетки, если она полностью гладкая. Используемый алгоритм усредняет нормали соседних треугольников, умноженные на угол соответствующих углов.

Расчет касательного пространства

Мы используем алгоритм касательного пространства Миккельсона для расчета касательного пространства для каждого кадра анимации на основе нормалей и UV сетки.

Оптимизация сетки

Сетки оптимизированы с помощью алгоритма изменения порядка лиц Форсайта, чтобы лучше использовать кеш преобразований GPU. Это также необходимо для подготовки к интер-предсказанию, которое предполагает, что порядок индексов соответствует полосам треугольников на сетке.

Материалы

Формат движка поддерживает несколько материалов на сетку. Для этого индексный буфер будет разбит на фрагменты для каждого материала. В настоящее время это делается путем анализа имени набора граней сетки в файле перегонного куба, где первое число в имени интерпретируется как материал ID (AlembicCompiler::GetMeshFaceSets).

Квантование и преобразование вершин

В целях сжатия все данные квантуются до целочисленных значений (AlembicCompiler::CompileVertices).

Позиции

Позиции сначала нормализуются до [0,1] по каждой оси, где 0 и 1 представляют минимальный и максимальный размер этой оси AABB всей анимации сетки. После этого позиция квантуется до uint16. Значение, представляющее 1, выбирается таким образом, чтобы было выделено достаточно битов, чтобы оно было лучше или достаточно хорошим, чтобы соответствовать указанной точности позиции, которую можно установить с помощью командной строки RC. Поэтому сетки меньшего размера используют меньший диапазон значений и, следовательно, лучше сжимаются.

УФ

Texcoords квантуются до uint16. Диапазон: 0–63. Значения выходят за пределы этого диапазона.

Цвета

Цвета сохраняются в виде четырех отдельных потоков красного, зеленого и синего, где каждое значение кодируется как одно uint8, представляющее диапазон 0–1.

Нормали и касательные

Касательные кадры, состоящие из нормальных, битангентных и касательных, преобразуются в QTangents, а затем каждый компонент квантуется в int16, где 10 бит используются для диапазона [-1, 1]. Отражение первого кадра принудительно применяется ко всем последующим кадрам, чтобы избежать проблем с интерполяцией. Это происходит только в крайних случаях, когда расчет касательного кадра дает разную ориентацию для разных кадров. (AlembicCompiler::EncodeQTangent)

Статические и анимированные данные

Каждый вершинный канал сетки (позиция, uv, цвет, QTangent) может быть либо static, либо динамическим. Статические данные сохраняются только один раз в начале файла, поэтому в каждом кадре сохраняются только анимированные каналы.

Оптимизация иерархии преобразований

В целях оптимизации иерархия преобразований перегонного куба максимально сглаживается. Все ненужные преобразования в иерархии удаляются, например. сетка с двумя динамическими преобразованиями и отсутствием одноуровневых элементов будет иметь только одно динамическое преобразование в формате движка (AlembicCompiler::CompileStaticDataRec). RC с подробным выводом распечатает полученное дерево для целей отладки.

Преобразования преобразуются в QuatTNS (кватернион со сдвигом и неравномерным масштабом) и сохраняются для каждого кадра, если они являются динамическими. Это еще не оптимизировано, поскольку скорость передачи данных не была проблемой по сравнению с вершинной анимацией.

Параллельная обработка кадров

Динамические сетки и преобразования обновляются для каждого кадра. Для преобразований влияние этого преобразования считывается из сцены Alembic в каждом кадре и вычисляется окончательный результат. Для сеток обновляются данные вершин, при необходимости перекомпилируются гладкие нормали и пересчитывается касательное пространство. Наконец, вершины снова преобразуются в формат движка (см. «Квантование и преобразование вершин»).

Для вывода имеется один буфер FIFO для каждой сетки и преобразования, который записывается компилятором и считывается из кодера в порядке кадров.

Поскольку это дорогостоящая операция, обновления запускаются как задания. Создается одно задание для каждой сетки и одно задание для всех обновлений преобразования кадров. Чтобы получить достаточно данных о параллелизме, несколько кадров обрабатываются параллельно. Поскольку выходные данные должны быть в порядке, для каждой сетки и преобразования используется буфер резервирования, и данные передаются в кодер только в том случае, если следующий кадр завершен. Если буфер резервирования переполнен, компилятор останавливается.

Задача кодировщика — взять квантованные данные и попытаться предсказать их так, чтобы результирующий остаток был как можно меньшим. Меньшие остаточные кадры приводят к лучшей степени сжатия. Для достижения этой цели формат геометрического кэша использует интер- (прогнозирование данных со ссылками только на один и тот же кадр) и внутреннее предсказание (прогнозирование со ссылками на другие кадры). В настоящее время нет прогнозов для анимированных преобразований, которые также сохраняются как полные QuatTNS в формате float. При необходимости здесь есть много возможностей для оптимизации.

Прогноз Интера

Индексные кадры могут использовать только внешнее предсказание, поскольку они должны иметь возможность декодироваться без какой-либо другой информации о кадре. Для позиций вершин и texcoords мы используем прогнозирование параллелограмма.

Значение следующей вершины прогнозируется на основе предыдущего треугольника с P = C + B – A. Сохраненное значение равно r = V – P, которое является остатком прогноза. Для этого предсказания кодер и декодер должны знать соседний треугольник. Мы храним расстояние до вершин, образующих прогнозируемый нами треугольник, как три значения uint16. Максимальное расстояние просмотра назад в настоящее время составляет 4096. Если совпадение не найдено, сохраняется только одно значение (0xFFFF), и мы просто используем предыдущее значение вершины в качестве прогнозируемого значения.

Чтобы максимизировать возможность прогнозирования, мы переставляем вершины на основе первого использования в массиве индексов (GeomCacheEncoder::OptimizeMeshForCompression). В результате получается массив вершин, в котором расстояние до вершин последнего треугольника сведено к минимуму.

Для цвета и QTangents мы не используем прогнозирование параллелограмма, а просто усредняем B и C, что приводит к несколько лучшим коэффициентам сжатия.

Внутрипрогнозирование

Для еще большей степени сжатия по умолчанию только каждый 10-й кадр является индексным кадром, а кадры между ними прогнозируются на основе двух предыдущих кадров, а также предыдущего и следующего индексных кадров (InterpolateMotionDeltaPredictor).

Формулы для предиктора:

  1. Пм = Фп + а * (Фп - Фпп)
  2. Пя = Яп +б*(ян - Яп)
  3. П = Пя +с*(Пм - Пя)

Предиктор движения (1) предполагает, что движение вершины продолжается в том же направлении. Поэтому он прогнозирует свое значение на основе значения предыдущего кадра плюс направление движения, полученное на основе двух последних кадров. Коэффициент a — это ускорение, которое может находиться в диапазоне [0, 2] и закодировано как uint8. Для первого кадра B прогноз движения не предусмотрен, поскольку мы не можем получить доступ к кадру B перед кадром I. Предиктор интерполяции (2) просто выполняет линейную интерполяцию между предыдущим и следующим I-кадром с коэффициентом b. Коэффициент b сохраняется как uint8. Наконец, оба предиктора объединяются в другой линейной интерполяции (3) с коэффициентом c, сохраненным как uint8. Это означает, что для каждого кадра и сетки мы храним три значения uint8 для предиктора.

Чтобы минимизировать пространство поиска для a, b и c, кодер сначала ищет оптимальную энтропию для (1) и (2) с помощью двоичного поиска и, наконец, выполняет еще один двоичный поиск с найденными значениями для (3).

Устройство записи имеет функцию получения данных от компилятора и кодировщика и сохранения их в конечном формате диска с выбранным сжатием блоков.

Структура файла

Сначала после компиляции данных static записывается заголовок, который содержит 64-битную подпись файла, номер версии, формат сжатия блока, поле флагов, количество кадров, общий размер несжатой анимации и AABB для всей анимации кэша Geom. Обратите внимание, что подпись изначально записывается нулями, чтобы предотвратить загрузку кэша в случае сбоя преобразования. Только в самом случае, если все остальное прошло успешно, пишем финальную подпись ("CRYCACHE").

Затем автор оставляет место для информации о кадре struct (SFrameInfo) для каждого кадра, который содержит тип кадра (кадр I или B, 32 бита), размер кадра (32 бита) и смещение кадра (64 бита). Размеры кадров и смещения могут быть известны только после компиляции, поскольку размер сжатия варьируется. Они также будут записаны в самом конце. Заголовок файла и информация о кадре хранятся в несжатом виде.

Следующим в файлах идет первый сжатый блок, содержащий данные static. Для всех сеток он содержит индексные данные (помните, что мы не поддерживаем изменения топологии), каналы вершин static, а для сеток с хотя бы одним анимированным каналом массив смежных треугольников uint16 для предсказателя параллелограмма. Для преобразований он содержит тип преобразования и QuatTNS для преобразований static.

Затем каждый кадр сохраняется в виде одного сжатого блока, каждый из которых содержит остаточные данные после прогнозирования для всех анимированных каналов и анимированных преобразований QuatTNS.

Блочные форматы сжатия

Мы поддерживаем три различных варианта сжатия блоков, сохранения, выкачивания и LZ4HC. Store просто хранит необработанные данные, что хорошо для скорости декодирования, но в основном реализовано как функция отладки. Deflate обеспечивает наилучшую степень сжатия, но декодирует его довольно медленно. LZ4HC очень быстро декодируется (на порядок быстрее, чем декодирование), но приводит к увеличению размера файлов примерно на 20%.

В целом LZ4HC кажется лучшим вариантом, если сцена, в которой используется кеш, интенсивно использует CPU из других систем, в противном случае, если время CPU не имеет значения, используйте Deflate.

Асинхронная запись

Каждый отправленный блок из кодера помещается в очередь, которую подбирают задания для сжатия. После сжатия они передаются в поток записи, который асинхронно записывает на диск.

Воспроизведение двигателя

  • Получает обновление каждого кадра от движка (CGeomCacheManager::StreamingUpdate)
  • Выдает асинхронные запросы на чтение диска для всех зарегистрированных и активных потоков.
  • Проблемы с распаковкой заданий, когда асинхронное чтение готово.
  • Каждый буфер распаковки и декодирования содержит несколько кадров, что позволяет получить их за одно последовательное чтение с диска. Каждый буфер всегда заканчивается индексным кадром.
  • Все буферы распределяются в куче фиксированного размера, которая выделяется при запуске движка (e_geomCacheBufferSize).
  • Каждый кадр имеет счетчик зависимостей декодирования. Они инициализируются значением 1 для индексных кадров, 3 для первого b-кадра после индексного кадра и 2 для всех остальных b-кадров. Инициализация выполняется при создании потока и при удалении буфера.
  • Когда задание уменьшает счетчик зависимостей другого кадра до нуля, оно запускает задание декодирования. Выполненные задания по распаковке уменьшают счетчик зависимостей задания по декодированию фрейма. Задания по декодированию индексных кадров. Выполненные задания индексного кадра уменьшают счетчик зависимостей следующего B-кадра и первого b-кадра после последнего индексного кадра. Задания B-кадра уменьшают счетчик зависимости следующего B-кадра. Это гарантирует, что каждый кадр всегда содержит необходимые ему данные (собственные распакованные данные, а для b-кадров — два предыдущих b-кадра, а также данные предыдущего и следующего индексного кадра).
  • Кадр помечается как готовый сразу после выполнения задания декодирования.
  • Если кэш воспроизводится, менеджер запускает задание асинхронного заполнения, которое принимает готовые декодированные данные и заполняет данные элемента рендеринга для кадра.
  • Читает данные static с диска.
  • Каждый кадр имеет struct со смещением, размером, типом и смещением относительно предыдущего и следующего индексного кадра.
  • Данные будут загружаться/выгружаться асинхронно во время выполнения, если узел рендеринга будет скрыт/открыт, если для e_streamCGF установлено значение 1.
  • Данные анимации будут прочитаны и полностью распакованы, если для кэша установлено значение «воспроизведение из памяти», а его размер не превышает ограничения, установленного e_GeomCacheMaxPlaybackFromMemorySize. При воспроизведении для этих кэшей будет выполняться только задание асинхронного заполнения.
  • Несколько кешей геометрии используют общие сетки static, если их хэш абсолютно идентичен.
  • Этот класс управляет созданием сеток рендеринга для кешей Geom и дедуплицирует их, если хэш тот же.
  • Создан и принадлежит прокси-серверу рендеринга объекта (в большинстве случаев GeomCache.lua).
  • Записывается у менеджера. Менеджер создает один объект потока для каждого зарегистрированного узла рендеринга.
  • Имеет интерфейс для изменения текущего воспроизведения и позиции потока (потоковая передача может выполняться в другой точке, чем воспроизведение, в случае, если воспроизведение необходимо продолжить из другого места)
  • Создает один элемент рендеринга для каждого материала в кеше.
  • Метод Render передает в движок отрисовку каждого элемента рендеринга.
  • Есть поддержка отрисовки CGF вместо кэша на определенном расстоянии (стенды). Существует три варианта замены: один для первого кадра, один для последнего кадра и один для всех остальных кадров. Если вы укажете только один для всех кадров, он также будет использоваться для первого и последнего кадра.
  • Также поддерживается автоматический запуск потоковой передачи при достижении определенного расстояния от кэша.
  • Ожидает асинхронного задания обновления в потоке рендеринга.
