Обзор

Физическая подсистема используется для физически имитировать зарегистрированные в нем объекты. Он имеет свой собственный набор объектов и геометрий, которые имеют аналоги в других частях движка. Например, симулированный рОбъект igid body может быть связан либо с сущностью Entity System, либо с частицей 3dengine. Обычно внешняя система запрашивает создание физического объекта определенного типа и сохраняет в нем указатель на себя в так называемых «внешних данных». Единственным исключением являются разрушаемые объекты, где физика создает новые физические объекты внутри себя и уведомляет остальную часть движка, которая, в свою очередь, создает сопутствующие объекты движка и связывает их с этими новыми физическими объектами.

По умолчанию физика выполняется в отдельном потоке и может иметь настраиваемое количество дополнительных рабочих потоков. В каждом кадре CrySystem запрашивает физику сделать шаг с учетом текущего времени кадра, и физика отправляет уведомления, когда результаты будут готовы. Обратите внимание: если физика не успевает за основным потоком, для возврата результатов может потребоваться более одного кадра основного потока. Таких ситуаций, конечно, следует избегать. Когда физический мир выполняет шаг, все входящие запросы на изменение к физическим объектам ставятся в очередь и выполняются только в начале следующего шага (чтобы они не мешали текущему моделированию). Это может затруднить отладку тех случаев, когда происходят определенные изменения, поэтому можно переключить физику для выполнения расчетов в основном потоке с помощью консольной переменной (sys_physics_enable_MT).

Физические уведомления приходят в виде событий (соответствующие структуры имеют имена с префиксом «EventPhys»). Чтобы их прослушивать, другие системы должны зарегистрировать прослушиватели с помощью вызова AddEventClient. Все прослушиватели являются «глобальными» и должны внутренне перенаправлять событие на определенные объекты механизма (при необходимости), используя информацию о физических внешних данных. Существует два типа событий — немедленные и зарегистрированные. Клиенты немедленных событий вызываются непосредственно из физического потока, поэтому функции должны быть потокобезопасными относительно основных потоков своих систем. Зарегистрированные события накапливаются во внутренней очереди и отправляются из основного потока ближе к концу основного шага. Как правило, немедленные события полезны для выполнения дополнительной симуляции в прослушивателе, поскольку в этом случае необходима точная синхронизация с физикой.

Обычно физические объекты имеют одну или несколько физикализованных геометрий. Физическая физикализация геометрии описана здесь: Регистрация геометрии в физике

Есть несколько Типы физических объектов. Более подробную информацию о настройке физических лиц можно найти здесь: Интерфейс физического объекта. Более подробную информацию о том, как работает внутреннее моделирование, можно найти. здесь.

Чтобы ускорить обнаружение широкофазовых столкновений (т.е. быстро найти объекты, которые потенциально могут столкнуться друг с другом), физика использует двумерную сетку. Каждый объект регистрируется в каждой ячейке, которой касается ограничивающая рамка, выровненная по оси, поэтому можно получить список объектов, которые касаются определенной ячейки. Учет сущностей в ячейках облегчается с помощью так называемых структур «сетки». Обратите внимание, что существует глобальный лимит на их количество, и как только он будет достигнут, дальнейшие изменения сетки не будут зарегистрированы, в результате чего сущности «теряют коллизии» (в журнале об этом будет предупреждение). Размер ячейки следует выбирать на основе общего размера карты и «плотности взаимодействия», т. е. ячейки меньшего размера могут дать более точный список потенциальных кандидатов на столкновение, но если объект занимает много ячеек, затраты на сбор списков из всех из них перевесят это преимущество. Grid-запросы доступны другим системам через GetEntitiesInBox функция.

Начиная с версии 5.2, несколько сеток моделирования поддерживаются.

Другими часто используемыми мировыми запросами являются Лучи и примитивная трассировка.

Различные эффекты окружающей среды можно моделировать с помощью Физические зоны.

В двигателе имеется несколько систем поломок, описанных здесь.

Взрывы являются одним из способов вызвать указанную поломку.

Увидеть физические объекты можно с помощью p_draw_helpers консольная переменная. В простейшем случае его можно просто установить на 1, чтобы отображать наиболее распространенный набор помощников, но его также можно настроить для включения различных типов объектов и помощников, используйте "p_draw_helpers?" для получения подробной информации.

Помимо профилировщика движка, физика имеет более высокоуровневый, включаемый с помощью p_profile. Дополнительные параметры профилирования: p_profile_entities чтобы показать список физических объектов, которые занимают большую часть времени моделирования, и p_profile_functions для отслеживания стоимости вызовов RayWorldIntersection, PrimitiveWorldIntersection и GetEntitiesInBox, поступающих из различных систем.
