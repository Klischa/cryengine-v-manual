Эта статья предназначена для CRYENGINE 3.4 или более ранней версии. Дерево выбора поведения и сценарии поведения старого стиля были заменены модульным деревом поведения в CRYENGINE 3.5 и более поздних версиях.

Начиная с CryENGINE 3.3.0 деревья поведения устарели и были заменены Деревья выбора поведения.

Любой класс может использовать дерево поведения/решений. Преимущества использования дерева поведения:

  • Единое место хранения знаний — все, что необходимо учитывать при принятии решения, находится в одном месте, где его можно легко модифицировать и поддерживать.
  • Единое место для принятия решений — дерево легко доступно и за ним легко следить.
  • Тактика предлагает способ организовать взаимодействие между несколькими (одными и теми же или разными) деревьями. Сюда входит AI!
  • Глобальные знания могут быть разделены между всеми пользователями дерева. Сюда входит AI!

Настройка дерева поведения

Вам нужно будет выполнить следующие шаги, чтобы настроить новое дерево поведения:

  1. Создайте новый профиль.
  2. Создайте новую диаграмму условий активации.
  3. Создайте новую древовидную диаграмму.
Создать новый профиль

(Расположение: Game\Scripts\BehaviorTree\Profiles)

Профиль — это XML-файл, который соединяет древовидную диаграмму с произвольным списком диаграмм условий активации. Вы обращаетесь к этому профилю по имени в коде, когда хотите начать использовать дерево в своем классе.

Типичный профиль выглядит следующим образом:

<BTProfile tree="TestClass">
  <ActivationConditions>
    <ActivationCondition name="TestClass" table="TestClass" doReset="0" />
  </ActivationConditions>
</BTProfile>

BTПрофиль: дерево — Этот атрибут определяет, какую древовидную диаграмму следует загрузить и использовать.

  • ActivationConditions - Дочерние элементы с именем ActivationCondition используются для определения новой диаграммы условий активации. Вы можете определить столько из них, сколько пожелаете.
  • ActivationCondition : имя — Этот атрибут определяет имя диаграммы условий активации, которую следует загрузить и использовать.
  • ActivationCondition : стол — Этот атрибут определяет имя, которое будет использоваться подтаблицей Lua для доступа к знаниям этой диаграммы.
  • ActivationCondition : doReset - Опционально; если указано значение TRUE, это означает, что если у пользователя уже загружена эта диаграмма знаний при переключении на этот профиль, содержащаяся информация будет сброшена обратно в исходное состояние. Значение FALSE (или, если вы не определили этот атрибут) означает, что информация будет сохраняться при переключении профиля.

Обратите внимание, что порядок определений условий активации на листе XML профиля важен! Ввод анализируется сверху вниз, поэтому таблицы внизу получают входные сигналы, отправленные им в последнюю очередь.

Создайте новую диаграмму условий активации.

(Расположение: Game\Scripts\BehaviorTree\ActivationConditions)

Диаграммы условий активации представляют собой электронные таблицы Excel. Имя файла должно совпадать с именем, указанным в XML-файле профиля. В таблице условий активации необходимо определить два важных листа:

  • Ценности - Эта диаграмма определяет значения по умолчанию для таблицы знаний. Это место, где вы можете определить значения для заполнения таблицы знаний.
    • Имя Столбец определяет имя переменной для таблицы знаний.
    • Начальное значение Столбец определяет начальное значение переменной.
    • Примечания Столбец — это необязательное место, где вы можете написать примечание о переменной, например, о том, как она используется.

TestClassAC.xls* Сигналы - Эта диаграмма определяет сигналы (входной код) для изменения таблицы знаний. Когда сигнал отправляется в дерево, он просматривается на этом листе. Вы можете изменить таблицу знаний по мере необходимости для каждого сигнала, используя дополнительные данные, которые могли быть переданы вместе с вызовом сигнала.

    • Сигнал Столбец определяет имя сигнала, который отправляется из кода для запуска этого действия. См. #Ввод дерева раздел ниже для более подробной информации.
    • Родитель Столбец является необязательным элементом управления. Вы можете указать имя сигнала, который также должен выполняться вместе с этим.
    • Ценности меняются Столбец определяет фрагмент кода Lua, который будет выполняться при вызове этого сигнала. См. #Правила языка Lua раздел ниже для более подробной информации.

Создайте новую табличную диаграмму

(Расположение: Game\Scripts\BehaviorTree\Trees)

Древовидные диаграммы представляют собой электронные таблицы Excel. Имя файла должно совпадать с именем, указанным в XML-файле профиля. В древовидной диаграмме необходимо определить два важных листа:

  • DAG - Здесь вы определяете ориентированный ациклический граф для дерева. Это дерево представлено в виде нисходящего потока с дочерними элементами, расширяющимися вправо. Родительские узлы представлены как объединенные ячейки.

TestClassTree.xls

Свойства узла — Это реализация дерева, в которой вы определяете выходные данные узлов и условные операторы для обхода дерева. Каждая строка представляет собой узел дерева, родительский или дочерний.

    • Путь столбец представляет родительский путь этого узла. Каждый шаг обхода обозначается точкой (.). Таким образом, если путь — Root -> Parent -> Child, родительский путь — «Root.Parent».
    • Имя Столбец представляет дочернее имя этого узла. Таким образом, если путь — Root -> Parent -> Child, имя дочернего элемента — «Child».
    • Импульс Столбец — это дополнительный способ перепрыгнуть через дерево. Если этот узел выполнит свое условие, обход дерева перейдет к местоположению, определенному путем в этом столбце.
    • Выбор ребенка столбец показывает, как проходят дочерние элементы этого узла. На данный момент единственным допустимым вариантом является «Приоритет».
    • SubTactic Столбец показывает, какой SubTactic необходимо запустить (и передать), чтобы обход дерева продолжился в этой ветке.
    • Сигнал Столбец представляет выходной сигнал, отправленный из дерева, когда узел проходит через него. См. #Вывод дерева раздел ниже для более подробной информации.
    • Условия активации Столбец определяет фрагмент кода Lua, который будет выполняться при переходе к этому узлу. Если оператор возвращает true, обход разрешается продолжить. Если этот узел является дочерним, дерево выбирает его в качестве нового листового узла и прекращает обход. См. #Правила языка Lua раздел ниже для более подробной информации.

Предварительные темы

Тактика

(Расположение: Game\Scripts\BehaviorTree\Tactics.xml)

Тактика — это способ координации двух или более деревьев путем ограничения прохождения определенных частей дерева до тех пор, пока достаточное количество кандидатов не будет готово удовлетворить эту тактику. Tactics.xml определяет все допустимые тактики. Подтактики этих определений затем используются во всех деревьях, где они действительны. В древовидной диаграмме необходимо определить два важных листа:

  • Тактика - Здесь вы определяете все действующие тактики, существующие в системе, и связываете их с подтактиками.
    • Имя столбец содержит название тактики.
    • Максимальное количество случаев тактики Столбец определяет максимальное количество экземпляров, которые можно создать для этой тактики. Значение «max» означает бесконечность. Если используется суб-тактика для этой тактики и требуется запустить другую, это не будет разрешено, если это количество превысит максимальное количество экземпляров.
    • Группа Использует В столбце указано, можно ли использовать тактику только внутри тактической группы или нет. См. #Группа Тактика раздел ниже для более подробной информации.
    • Максимальное количество экземпляров группы Столбец определяет максимальное количество экземпляров, которые можно создать для этой тактики PER GROUP. Это игнорируется, если тактика не использует группы. Значение «max» означает бесконечность. Если подтактика для этой тактики используется группой, а другая хочет быть запущена той же группой, это не будет разрешено, если это количество превысит максимальное количество экземпляров.
    • Поведение, когда актеров меньше Min Столбец определяет, как следует действовать с тактикой, когда для участия в ней уже недостаточно пользователей. Единственный действительный вариант для этого сейчас - "DESTROY_TACTIC".
    • SubTactic Столбец определяет подтактику, связанную с этой тактикой. Для нескольких субтактик создайте новую пустую строку ниже и заполните только этот столбец названием следующей субтактики.

Tactics.xls

Требования - Здесь вы определяете все действующие субтактики и их требования.

    • Имя столбец содержит название субтактики.
    • Дерево Столбец определяет, какое дерево можно считать пользователем этой подтактики. Свойства, описанные в следующих столбцах, отражаются на этом дереве. Для нескольких пользователей дерева создайте новую пустую строку ниже и заполните имя дерева и данные для следующего набора столбцов, которые отражаются в этом дереве.
    • Мин актеров для начала Столбец определяет, сколько участников должно быть кандидатами на эту тактику, прежде чем она сможет начаться.
    • Минимальные актеры для участия Столбец определяет, сколько актеров необходимо для поддержания тактики. Если слишком много выпадет, тактика будет остановлена.
    • Макс актеры Столбец определяет, какое максимальное количество участников может присоединиться к этой тактике. Если захотят еще больше, они будут вынуждены попытаться создать новый экземпляр этой тактики.
    • Функция заказа — это фрагмент кода Lua, выполняемый для сортировки потенциальных кандидатов. Передаются два пользователя (A и B). Возвращаемое значение TRUE означает ранжирование A выше, чем B, в качестве кандидата для этой тактики. Будут выбраны кандидаты с самым высоким рейтингом, вплоть до максимального количества. См. #Правила языка Lua раздел ниже для более подробной информации.

Тактика Групп

Пользователей можно поместить в группу, получив уникальный идентификатор группы Tactics. Это может быть любое указанное вами целочисленное значение. Когда пользователь запускает суб-тактику, если этот пользователь является частью тактической группы, только другие члены его группы могут присоединиться к нему в этой суб-тактике. Это необязательный метод выделения общего пула потенциальных кандидатов.

Реализация пользовательского класса дерева поведения

Любой класс может загрузить и использовать дерево поведения, унаследовав его от класса. IBSSProfileUser абстрактный базовый класс. Наследуя его, вы можете затем загрузить дерево поведения и подключить его к классу через возвращаемый уникальный идентификатор.

IBSSProfileUser Интерфейс

Этот ABC должен быть унаследован классом, который будет отвечать за обработку ввода и вывода в дерево. Функции virtual следующие:

  • GetBTUserName - Вернуть уникальное имя пользователя для этого пользователя дерева. Используется в целях отладки.
  • GetBTUserTable - Верните IScriptTable*, к которому можно легко получить доступ в условиях активации и древовидных диаграммах. См. #Правила языка Lua раздел для более подробной информации.
  • GetBTUserBlackBoard - Вернуть IBlackBoard*, который следует использовать для хранения информации, относящейся к дереву и его обходу. Полезно для целей AI.
  • CanBTUserTreeRun - Верните TRUE, если дерево разрешено для запуска. Это вызывается, когда таблица знаний изменилась и дерево необходимо обновить. Возврат FALSE здесь может остановить обновление дерева.
  • OnBTUserEvent - Вызывается, когда дерево вывело значение. См. #Вывод дерева раздел ниже для более подробной информации.
Связывание с деревом

Чтобы связать класс с деревом, вы должны использовать метод InitNewUser функционировать в IBSSProfileManager объект, возвращенный из AISystem. Введите имя профиля для загрузки. А TBSSProfileUserId возвращается значение, которое вы должны сохранить. Используйте это в будущих вызовах для отправки входных данных в дерево или выполнения других операций над ним.

В процессе очистки обязательно используйте RemoveUser функция удаления дерева.

Другие интересные функции:

  • SwitchUserProfile - Вызов, чтобы изменить профиль, который должен использовать класс. Это полезный способ легко перейти к новому дереву во время выполнения. Возвращается новый UserId.
  • ResetUser - Вернуть дерево и таблицы знаний в исходное состояние.
  • EnableUser - Полностью включать/выключать дерево на пользователе.

Ввод дерева

Чтобы отправить входные данные в диаграммы условий активации, вам следует использовать SendUserInput функционировать в IBSSProfileManager объект, возвращенный из AISystem. Вы должны передать свой уникальный TBSSProfileUserId возвращается, когда вы ссылаетесь на дерево, описанное выше. Имя сигнала и дополнительные данные передаются во все диаграммы условий активации сверху вниз, как определено в XML-листе профиля.

Вывод дерева

Когда дерево имеет выходные данные для отправки обратно, они отправляются через метод OnBTUserEvent функция, унаследованная от IBSSProfileUser. Отправленные аргументы следующие:

  • событие - Событие, которое было вызвано. Допустимые значения:
    • eBTUE_OnNodeSignal - Отправляется, когда дерево встретило сигнал узла (узел был пройден)
    • eBTUE_OnNewLeafNode - Отправляется, когда дерево перешло к новому конечному узлу (отправляется каждый кадр, пока вы не разрешите изменение узла!)
    • eBTUE_OnDecisionMade - Отправляется, когда дерево приняло решение (смена узла одобрена)
  • pTree - Объект дерева личного поведения. Используйте его для принятия изменений узлов на новых конечных узлах или для взаимодействия с деревом по мере необходимости.
  • sSignal - Выходной сигнал из дерева.
  • pArgValue — Значение аргумента, которое было отправлено вместе с последним вводом, который вызвал обновление дерева, в результате чего было отправлено это событие.

Когда eBTUE_OnNewLeafNode получено, дерево информирует вас о том, что был обнаружен новый листовой узел. Однако вы должны разрешить дереву переключиться на этот листовой узел, т. е. принять решение. Вы можете сделать это, позвонив в AllowNodeChange функция для объекта дерева, отправленного в качестве аргумента функции. Если вы этого не сделаете, дерево продолжит отправлять это событие каждый кадр. Существуют причины, по которым вы можете захотеть отложить принятие решения, например, чтобы ввести задержку или предотвратить постоянные изменения состояния из-за притока новых данных. В любом случае вы не получите eBTUE_OnDecisionMade пока вы не разрешите изменение узла.

Пример класса

Вот пример класса, который загружает наш TestTree, определенный выше, и использует его.

// Test behavior tree using class
class CBehaviorTreeTest : public IBSSProfileUser
{
public:
  CBehaviorTreeTest();
  virtual ~CBehaviorTreeTest();

  // Sent when action is processed
  void OnButtonState(bool bDown);
  void SetGlobalValue(bool bValue);

  // IBSSProfileUser
  bool GetBTUserName(string &sOut) const;
  bool CanBTUserTreeRun() const;
  void OnBTUserEvent(EBTUserEvents event, IPersonalBehaviorTree *pTree, const string& sData, const ScriptAnyValue* pArgValue = NULL);
  //~IBSSProfileUser

private:
  TBSSProfileUserId m_userId;
};
//////////////////////////////////////////////////////////////////////////
CBehaviorTreeTest::CBehaviorTreeTest()
: m_userId(g_uBTUserId_Invalid)
{
  // Link to tree and get the unique Id back
  IBSSProfileManager *pManager = gEnv->pAISystem->GetBSSProfileManager();
  if (pManager)
  {
    pManager->InitNewUser(this, "TestClass", m_userId);
  }

  CRY_ASSERT_MESSAGE(m_userId != g_uBTUserId_Invalid, "CBehaviorTreeTest failed to init with the \"TestClass\" BT profile");
}

//////////////////////////////////////////////////////////////////////////
CBehaviorTreeTest::~CBehaviorTreeTest()
{
  // Release the tree
  IBSSProfileManager *pManager = gEnv->pAISystem->GetBSSProfileManager();
  if (pManager && m_userId != g_uBTUserId_Invalid)
  {
    pManager->RemoveUser(m_userId);
    m_userId = g_uBTUserId_Invalid;
  }
}

//////////////////////////////////////////////////////////////////////////
void CBehaviorTreeTest::OnButtonState(bool bDown)
{
  IBSSProfileManager *pManager = gEnv->pAISystem->GetBSSProfileManager();
  if (pManager && m_userId != g_uBTUserId_Invalid)
  {
    // Send the input signal into our Activation Conditions chart.
    // The 'data' property will be set to the value of 'bDown'.
    pManager->SendUserInput(m_userId, "SetButtonState", bDown);
  }
}

//////////////////////////////////////////////////////////////////////////
void CBehaviorTreeTest::SetGlobalValue(bool bValue)
{
  IBSSProfileManager *pManager = gEnv->pAISystem->GetBSSProfileManager();
  if (pManager)
  {
    // Send a signal to the Global Activation Conditions chart.
    // The 'data' property will be set to the value of 'bValue'.
    pManager->SendGlobalSignal("SetTestValue", bValue);
  }
}

bool CBehaviorTreeTest::GetBTUserName(string &sOut) const
{
  // A good unique name for our tree.
  sOut = "CBehaviorTreeTest";
  return true;
}

//////////////////////////////////////////////////////////////////////////
bool CBehaviorTreeTest::CanBTUserTreeRun() const
{
  // Tree can always be ran!
  return true;
}

//////////////////////////////////////////////////////////////////////////
void CBehaviorTreeTest::OnBTUserEvent(EBTUserEvents event, IPersonalBehaviorTree *pTree, const string& sData, const ScriptAnyValue* pArgValue)
{
  switch (event)
  {
    // Sent when a parent node has been traversed which defined some signal data.
    case eBTUE_OnNodeSignal:
    {
      CryLogAlways("[CBehaviorTreeTest] Event=eBTUE_OnNodeSignal Data=%s", sData.c_str());
    }
    break;

    // Sent when a new leaf node has been hit.
    case eBTUE_OnNewLeafNode:
    {
      CryLogAlways("[CBehaviorTreeTest] Event=eBTUE_OnNewLeafNode Data=%s", sData.c_str());

      // Call to allow the tree to switch to this leaf node (make a decision).
      // NOTE: Decision won't be made until we call this! We could stall here for a moment!
      pTree->AllowNodeChange();
    }
    break;

    // Sent when the tree has made a new decision (new leaf node and change was allowed to be made).
    case eBTUE_OnDecisionMade:
    {
      CryLogAlways("[CBehaviorTreeTest] Decision Made! %s", sData.c_str());
    }
    break;

    default:
      CRY_ASSERT_MESSAGE(false, "CBehaviorTreeTest received unhandled user event");
      break;
  }
}

Правила языка Lua

Имея дело с фрагментами кода Lua, присутствующими в условиях активации или древовидных диаграммах, есть несколько конкретных вещей, на которые вы можете ссылаться в коде Lua.

  • г - Эту таблицу можно использовать для доступа ко всем глобальным значениям, определенным в таблице глобальных условий активации.
    (г["SomeVariable"])
  • а - Эту таблицу можно использовать для доступа к локальным значениям, определенным в диаграммах условий активации профиля. Каждая таблица условий хранится в ней как дочерняя таблица с именем, указанным в XML-листе профиля.
    (а.TestValue["SomeVariable"])
  • userTbl - Эту таблицу можно использовать для доступа к таблице сценариев, возвращаемой из кода, через пользовательскую GetBTUserTable функция.
    (userTbl:CallSomeFunc())

В коде функции упорядочивания тактики есть другой набор конкретных вещей, на которые вы можете ссылаться в коде Lua.

  • а - Эту таблицу можно использовать для доступа к таблице сценариев, возвращаемой из кода, через пользовательскую GetBTUserTable функция для пользователя А тактики.
    (а:CallSomeFunc())
  • б - Эту таблицу можно использовать для доступа к таблице сценариев, возвращаемой из кода, через пользовательскую GetBTUserTable функция для пользователя B тактики.
    (б:CallSomeFunc())
