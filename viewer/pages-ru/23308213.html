Обзор

Используя пакетную обработку, компилятор ресурсов (RC) может обрабатывать все файлы ресурсов для конкретной платформы только за один раз.

Для этого вы вызываете RC с помощью /работа переключатель, в котором вы указываете путь к файлу задания XML.

Например, для создания основной части ресурсов SDK в том виде, в котором они поставлены, мы используем:

Bin64\RC\rc.exe /p=PC /job=Bin64\RC\RCJob_Build_SDK.xml

Дополнительные примеры файлов Job XML вы можете посмотреть в разделе Bin64\RC папка пакета SDK.

Формат задания XML

Формат задания XML задается с помощью файла XML, который вы можете редактировать с помощью любого текстового редактора по вашему выбору.

RC выполнит файл сверху вниз, анализируя и выполняя (при необходимости) содержимое пакетного сценария.

Корневой тег файла задания XML: <RCJobs>:

<RCJobs>
  <!-- contents of the file -->
</RCJobs>

Свойства

Важно понимать, что задание XML — это template для сборки, которая специализирована с использованием параметров, передаваемых в командной строке. Вообще говоря, наиболее важным являетсяп'параметр (платформа).

Во время пакетного выполнения каждый параметр командной строки преобразуется в свойство, как и любое другое свойство RC.

Чтобы просмотреть список свойств, используемых RC, запустите «rc.exe /help».

Доступ к значениям свойств можно получить внутри сценария Job XML с помощью конструкции ${propertyname}, которую можно использовать для установки других свойств или для условного выполнения частей пакета.

Свойства по умолчанию

В зависимости от сложности пакетного сценария количество используемых свойств может стать значительным, а ввод значений в командной строке может стать утомительным.

Таким образом, вы можете указать значения по умолчанию для свойств в начале файла задания XML. Для этого используйте <DefaultProperties> XML блок.

В сборке SDK мы указываем имена папок по умолчанию (среди прочих) для ресурсов, используя свойства по умолчанию:

<DefaultProperties game="GameSDK" engine="Engine" loc="Localization" />

Свойства по умолчанию можно использовать для инициализации значений до того, как остальная часть пакетного сценария будет выполнена с разумными значениями по умолчанию.

Параметры командной строки. Свойства override, указанные в блоке DefaultProperties.

Вычисленные свойства

Возможно, вы захотите динамически вычислять свойства в зависимости от значений других свойств.

Можно передать «флаг функции» и соответствующим образом настроить свойства преобразования (т. е. свойство, которое управляет другими свойствами). Для этого используйте <Свойства> XML блок.

В SDK мы можем передать свойство "streaming" или, если оно не указано, мы устанавливаем его в соответствии со свойством платформы 'п'.

Мы динамически выводим свойство do_streaming, которое позже используем для управления потоковой передачей текстур.

<DefaultProperties streaming="auto" />
<if streaming="auto">
  <if p="PC">
    <Properties do_streaming="0" />
  </if>
  <if p="X360">
    <Properties do_streaming="1" />
  </if>
</if>
<ifnot streaming="auto">
  <Properties do_streaming="${streaming}" />
</ifnot>

В отличие от свойств по умолчанию, свойства, определенные через <Свойства> не являются условными, значение свойства будет обновляться независимо от любых параметров командной строки с тем же именем.

Условные предложения (если и если нет)

Иногда имеет смысл выполнить только определенный этап обработки для конкретной платформы или попеременную обработку конкретных активов в зависимости от какого-либо свойства.

Для этого используйте <если> XML блок:

<if propertyname='compare'>
  <!-- only evaluated if the value of property 'propertyname' is equal to 'compare' -->
</if>
 
<ifnot propertyname='compare'>
  <!-- only evaluated if the value of property 'propertyname' is not equal to 'compare' -->
</ifnot>
 
<!-- it's also possible to compare to another property value -->
<if propertyname='${anotherproperty}' />

Область применения

Свойства в сценарии RC имеют определенную область действия. Обычно XML вычисляется последовательно, а значения свойств являются постоянными.

Однако следующие теги открывают новую область действия свойств:

  • Задание: любые значения свойств, указанные (как атрибуты XML) внутри «тега задания», относятся к области этого вызова задания.
  • Запуск: любые значения свойств, указанные (как атрибуты XML) внутри тега «Выполнить», относятся к этому вызову, и любые свойства, введенные или измененные вызванным XML, будут забыты после возврата «Выполнить».

Используя эти конструкции, вы можете написать «подпрограмму» внутри XML, которую можно вызывать несколько раз с разными переменными (где значения переменных хранятся в именованных свойствах).
Например:

<MySubRoutine>
  <!-- Takes parameters "what" and "destination" -->
  <Job Input="${What}" Zip="${Destination}/MySubRoutine.pak" />
</MySubRoutine>

<MainRoutine>
  <!-- Call subroutine for packing *.foo into C:/Some/Path/MySubRoutine.pak -->
  <Run Job="MySubRoutine" What="*.foo" Destination="C:/Some/Path" />
</MainRoutine>

В этом примере предположим, что 'MainRoutine' был выполнен (либо с использованием командной строки /jobtarget=MainRoutine или <Run Job="MainRoutine"/> как дочерний элемент корня XML).
<Выполнить> будет использоваться для «вызова» «подпрограммы» «MySubRoutine» по имени. Атрибуты What и Destination указаны в примере как inline и будут видны внутри MySubRoutine.
Как только «вызов» «MySubRoutine» «вернётся» к «MainRoutine», значения What и Destination вернутся к своему предыдущему значению (если таковое имеется).

Любые значения свойств, видимые в данный момент, могут быть использованы и изменены в «MySubRoutine», однако любые изменения или новые введенные значения свойств не сохранятся при «возврате».

Из соображений читаемости или повторного использования вы также можете использовать <Свойства> или <DefaultProperties> теги при использовании «подпрограмм».
Например:

<RCJobs>
  <Foo>
    <Properties A="a" />
    <!-- Do something with A B and C --> 
  </Foo>
  <Bar>
    <DefaultProperties B="b" />
    <Properties A="x" />
    <Run Job="Foo" C="c" />
    <!-- Here, A==x -->
  </Bar>
  <Run Job="Bar" />
</RCJobs>

Предположим, вы запустили этот пример файла, значения A, B и C будут равны «a», «b» и «c» соответственно в строке с комментариями.
Значение «x» A передается в Foo, но затем перезаписывается. Однако как только Foo вернется, значение «x» будет восстановлено.
Кроме того, можно было бы изменить значение B, передав параметр командной строки «/B=x» при запуске задания, чтобы изменить поведение по умолчанию.

В общем, вам всегда следует сохранять следующий порядок блоков в файле задания XML, чтобы поведение RC соответствовало ожиданиям при чтении файла XML:

  • DefaultProperties блоков
  • Блоки свойств
  • Блоки заданий
  • Запуск блоков

Задания по преобразованию активов

Преобразование активов определяется через <Вакансия> XML блокируется и выполняется последовательно (хотя части некоторых заданий могут выполняться параллельно — см. потоки свойств RC).

Задания перебирают набор файлов (в локальной файловой системе), таким образом вызывая обработку RC для каждого файла в наборе, как если бы RC был конкретно вызывается для этого файла (при использовании свойств, установленных в данный момент в пакетном сценарии для выполнения).

В общем, преобразование ресурсов — это процесс с потерями, и вам всегда следует хранить исходные файлы отдельно от результатов преобразования.
Конвертированный файл обычно невозможно преобразовать обратно в исходный файл.
RC предназначен для получения данных из одного места (указанного с помощью «sourceroot») и записи преобразованных данных в другое место (указанное с помощью «targetroot»).

Синтаксис блока <Job> XML выглядит следующим образом:

<Job sourceroot="path to folder inside which to search for files" input="file mask of files to select for processing" targetroot="path to folder in which to store the processed files" conversion_parameter="some value" />

В общем, имеет смысл выполнять только один тип преобразования внутри одного блока задания, поэтому «вход» обычно задается маской расширения файла, например: *.tif

Вот пример обработки текстур из файлов CryTiff (*.tif) в файлы, специфичные для платформы (обычно *.dds для PC):

<ConvertJob>
  <Job sourceroot="${source_game_folder}" input="*.tif" targetroot="${target_game_folder}" imagecompressor="CTsquish" streaming="0" />
</ConvertJob>

Это задание будет искать все файлы CryTiff по значению свойства с именем «source_game_folder» и конвертировать их с помощью CTsquish, а не подготовки к потоковой передаче ресурсов. Результат будет сохранен в значении свойства с именем «target_game_folder».

Набор значимых параметров преобразования, которые можно установить, зависит от набора типов файлов, которые соответствуют ограничениям набора входных данных.

Таким образом, разумно ограничить набор файлов одним типом файлов и указать параметры преобразования только для этого конкретного преобразования, чтобы файл Job XML был понятен.

Список значимых параметров преобразования для данного преобразования можно найти, вызвав «rc.exe /help».

Как правило, при преобразовании учитывается относительный путь от свойства «sourceroot» до соответствующего файла и используется тот же относительный путь для хранения «targetfile», но относительно свойства «targetroot».

Обратите внимание, что любое задание, запущенное с помощью SourceRoot==TargetRoot, не будет соответствовать никаким файлам (и, следовательно, ничего не будет делать), независимо от реальных файлов.
В RC есть несколько преобразований, которые не меняют имя исходного или целевого файла (поскольку это может вызвать проблемы), и хотя есть несколько преобразований, которые могут работать, для простоты это рассматривается как ошибка.

Сквозной (копия)

Иногда имеет смысл не выполнять никакой обработки для данного набора файлов.

В этом случае вы можете установить для специального параметра преобразования «copyonly» значение 1, что будет просто копировать все файлы, соответствующие ограничениям набора входных данных, в эту целевую папку:

<CopyJob>
  <Job sourceroot="${source_folder}" input="*.xml" targetroot="${target_folder}" copyonly="1" />
</CopyJob>

Набор входов

Набором входов можно дополнительно управлять с помощью следующих специальных свойств:

  • рекурсивный: (по умолчанию 1).
    Если установлено значение 0, поиск будет учитывать только файлы в папке «sourceroot», но не в подпапках.
  • ввод: (по умолчанию — «*»).
    Соответствует относительному пути к указанным выражениям и передает только файлы, соответствующие одному или нескольким выражениям.
    Используйте «*», чтобы указать ноль или то, что в этом месте допускается больше символов.
    Разделите несколько выражений с помощью точки с запятой: «*.a;*.b» будет передавать все имена файлов, заканчивающиеся на «.a» или «.b».
  • исключить: (по умолчанию нет).
    Аналогично «входу», за исключением того, что файлы, соответствующие выражению(ям), не передаются.
    Исключение переопределяет «вход», поэтому файл, соответствующий обоим выражениям, будет NOT во входном наборе.
  • файл списка (по умолчанию нет).
    Открывает указанное выражение как текстовый файл и ограничивает входной набор любым файлом в списке.
    Файл списка представляет собой текстовый файл, каждый файл которого находится на отдельной строке.
  • exclude_listfile (по умолчанию нет).
    Как и исключение «listfile», любой файл, соответствующий списку, не передается.
    Исключение переопределяет 'listfile', поэтому файл в обоих списках будет NOT во входном наборе.

Переопределение типа файла

Иногда вам может потребоваться интерпретировать определенный файл определенного типа, даже если у него нет соответствующего расширения.

В этом случае вы можете использовать свойство перезаписать расширение чтобы заставить RC выбрать конвертер для переопределенного расширения, т. е. вместо конвертера, который он выбрал бы для фактического расширения.

Например, чтобы принудительно преобразовать файл .mtl, как если бы он был файлом XML, вы можете использовать:

<Job input="*.mtl" overwriteextension="xml" ...rest of the job... />

Упаковка Вакансии

После того как вы конвертировали и/или скопировали все файлы, которые должны быть предоставлены в файловой системе конечного пользователя, вы можете упаковать их в файлы *.pak.

Для этого используйте <PakJob> сгруппировать и добавить <Вакансия> блоки с входными наборами, которые следует добавить в *.pak.

Ниже приведен пример создания файла Textures.pak, содержащего все файлы *.dds, ранее преобразованные из CryTIFF:

<PakJob>
  <Job sourceroot="${processed_files_folder}" input="*.dds" zip="${target_folder}\Textures.pak" />
</PakJob>

При желании вы можете указать свойство «zip_compression», которое управляет сжатием.

Если установлено значение 0, файл *.pak не будет сжиматься. Это может подойти для некоторых файлов, которые часто требуют поиска файлов во время выполнения.

Запуск заданий

После того, как вы указали все нужные вам группы заданий, вы можете запустить их с помощью <Выполнить> блок:

<ConvertJob>
  <!-- conversion jobs -->
</ConvertJob>
 
<CopyJob>
  <!-- copy jobs -->
</CopyJob>
 
<PakJob>
  <!-- packing jobs -->
</PakJob>
 
<Run Job="ConvertJob"/>
<Run Job="CopyJob"/>
<Run Job="PakJob"/>
Поскольку файл анализируется сверху вниз, убедитесь, что группы заданий указаны до блоков <Run>, которые ссылаются на них.
