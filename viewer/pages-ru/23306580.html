Обзор

Эта система позволяет игровому коду автоматически выполнять реакцию, соответствующую контексту, когда персонаж получает удар (HitReaction) или умирает (DeathReaction).

Когда у актера обнаруживается попадание или смерть, система оценивает список реакций, которые имеет актер, и выбирает первую, соответствующую критериям проверки. После этого он выполняет его. Реакции на попадание и реакции на смерть очень похожи, но последние всегда заканчиваются тем, что актер превращается в тряпичную куклу.

Некоторые правила

  • Реакция на попадание никогда не может прервать другую текущую реакцию на попадание.
  • Реакция смерти всегда может прервать текущую реакцию реакции на попадание. UNLESS реакции были явно запрещены с помощью события анимации «ForbidReactions».
  • Реакции должны уведомить систему о своем завершении. Если это анимационные реакции, об окончании автоматически сообщается при достижении конца анимации или при запуске анимационного события «DeathReactionEnd» во время воспроизведения реакции смерти. В системе предусмотрен резервный режим, поэтому, если реакция выполняется более 3 секунд (возможны изменения), ее завершение происходит принудительно.

Реакции

Реакции содержатся в таблице LUA, которая анализируется из файла данных XML, путь к файлу которого находится внутри таблицы BasicActor. fileHitDeathReactionsParamsDataFile свойство, поэтому его можно настроить для каждого архетипа. В будущем это может измениться, поэтому он использует PropertyInstances, чтобы иметь возможность настраивать путь к файлу для каждого экземпляра актера на уровне (см. Раздел «Планы на будущее») и формат которого описан в файле определения Scripts/GameRules/HitDeathReactions_Defs.xml" (см. XML Загрузчик документации, чтобы понять, как код анализирует файл данных и почему нам нужен отдельный файл определений).

Каждая реакция обеспечивает:

  • необязательный validationFunc свойство (указав имя функции lua внутри HitDeathReactions.lua который содержит настроенный код проверки).
  • необязательный reactionFunc свойство (указав имя функции lua внутри HitDeathReactions.lua который содержит настроенный код выполнения).
  • Некоторые другие свойства, которые будут использоваться для шагов проверки и/или выполнения (подробнее читайте ).

Валидация(и)

Система просматривает список реакций в том порядке, в котором они определены в файле данных, и оценивает их. Реакция выполняется OK, если какая-либо из ее проверок прошла успешно. Каждая проверка может выбрать, какой код проверки будет запущен, чтобы узнать, действителен ли он. Этот код проверки может использовать свойства внутри этой проверки. По умолчанию при проверках используется некоторый код LUA и C++, который выполняет код проверки по умолчанию, но если есть конкретный случай, требующий дополнительных/других проверок, есть также возможность указать для этого настраиваемую функцию проверки LUA или C++. Более подробно о том, как писать проверки реакций в эта глава страницы «Реакции» XML Формат описания.

Проверка по умолчанию

Если настраиваемая функция проверки не указана, система запускает код проверки по умолчанию.

Если CVar g_hitDeathReactions_useLuaDefaultFunctions верно, код проверки по умолчанию состоит в вызове метода LUA HitDeathReactions:DefaultValidation() (который внутренне вызывает метод C++ CHitDeathReactions::IsValidReaction()), в противном случае он вызывает напрямую код C++ CHitDeathReactions::IsValidReaction().

Для получения дополнительной информации о методе и свойствах проверки по умолчанию проверьте .

Пользовательская проверка

Пользовательские исполнения могут быть написаны на LUA или C++:

LUA Пользовательские функции проверки

Это функции LUA, которые получают два аргумента: таблицу параметров реакции для оцениваемой реакции и таблицу hitInfo с данными попадания, вызвавшего событие Hit или Death. Ожидается, что он вернет логическое значение true или false в зависимости от того, подтверждена реакция или нет.

Пример:

function HitDeathReactions:ExampleValidation(validationParams, hitInfo, causedDamage)
  -- uses the default C++ validation code and additionally checks for the damage caused by the hit to be greater than 80
  local bValidated = self.binds:IsValidReaction(validationParams, hitInfo) and (causedDamage > 80);

  return bValidated;
end

LUA Функции проверки не следует использовать в финальных сборках, поскольку они могут очень замедлить процесс попадания.

Пользовательские функции проверки C++

Зарегистрироваться можно через CCustomReactionFunctions объект (который вы можете получить из CHitDeathReactionsSystem экземпляр) и метод RegisterCustomValidationFunction.
Их подпись bool (CActor&, const SReactionParams::SValidationParams&, const HitInfo&, float fCausedDamage). например,

// ...
const CCustomReactionFunctions& customReactions = g_pGame->GetHitDeathReactionsSystem().GetCustomReactionFunctions();
customReactions.RegisterCustomValidationFunction("DeathImpulse_Reaction", functor(*this, &CMyClass::FallNPlay_Validation));
// ...

Исполнение

После успешной проверки реакции система выполняет ее. Уже существует некоторый код LUA и C++, который запускает код выполнения по умолчанию, но если есть конкретный случай, требующий дополнительных эффектов, для этого также можно использовать настроенную функцию выполнения LUA.

Для получения дополнительной информации о методе выполнения по умолчанию проверьте .

Выполнение по умолчанию

Если настраиваемая функция выполнения не указана, система запускает код выполнения по умолчанию.

Если CVar g_hitDeathReactions_useLuaDefaultFunctions верно, код выполнения по умолчанию состоит из вызова метода LUA HitDeathReactions:DefaultHitReaction() (который внутренне вызывает метод C++ CHitDeathReactions::ExecuteHitReaction()), в противном случае он вызывает напрямую код C++ CHitDeathReactions::ExecuteHitReaction().

Выполнение по умолчанию делает следующее:

  • Воспроизводит анимацию с использованием графа анимации, устанавливая для входного сигнала указанное значение и (необязательно) некоторые варианты ввода. OR...
  • Воспроизводит анимацию, минуя граф анимации, используя имя анимации, определенное в файле анимации .cal.
Пользовательское исполнение

Пользовательские исполнения могут быть написаны на LUA или C++:

LUA Пользовательские функции выполнения

Это функции LUA, которые получают только один аргумент: таблицу параметров реакции для выполняемой реакции. Его возвращаемое значение игнорируется.

Пример:

function HitDeathReactions:ExampleExecution(reactionParams)
  -- Enables Fall and Play on the actor and notifies the end of the current reaction after 1 second
  self.entity.actor:Fall({x=0,y=0,z=0});
  Script.SetTimer(1000, self.binds.EndCurrentReaction, self.binds);
end
Пользовательские функции выполнения C++

Зарегистрироваться можно через CCustomReactionFunctions объект (который вы можете получить из CHitDeathReactionsSystem экземпляр) и метод RegisterCustomExecutionFunction.
Их подпись void (CActor&, const SReactionParams&, const HitInfo&). например,

// ...
const CCustomReactionFunctions& customReactions = g_pGame->GetHitDeathReactionsSystem().GetCustomReactionFunctions();
customReactions.RegisterCustomExecutionFunction("DeathImpulse_Reaction", functor(*this, &CMyClass::DeathImpulse_Reaction));
// ...

Некоторые пользовательские функции выполнения C++ уже зарегистрированы внутри класса CCustomReactionFunctions. См. void CCustomReactionFunctions::RegisterCustomFunctions()

Сеть

Реализация обязательно будет изменена, поэтому этот раздел представляет собой скорее список наблюдений, чем что-либо еще.

  • Текущая реализация запускает коды проверки и выполнения на обеих сторонах (клиенте и сервере). Это может вызвать проблемы из-за того, что обе стороны не могут иметь одинаковое состояние и контекст в любой момент, поэтому для одного и того же попадания проверки могут возвращать разные результаты в зависимости от проверяемой стороны. Способ решения этой проблемы — запустить код проверки только на локальном компьютере (не обязательно на сервере, хотя это может вызвать некоторые другие проблемы, поскольку расчет ущерба обрабатывается только на сервере), который сгенерировал попадание, и сериализовать идентификатор (т. е. индекс) для выбранной реакции на другие сеансы. Это также упростит выбор случайной вероятности.
  • Реакция на попадание не работает по сети в текущей кодовой базе.

Потоковое вещание

Чтобы свести к минимуму объем памяти, занимаемый анимацией реакций, система использует стратегию потоковой передачи, описанную ниже.

Поскольку мы не можем предсказать, какая реакция будет воспроизведена следующей, и нам нужно немедленное воспроизведение анимации (мы не можем позволить себе 1 секунду потоковой передачи между ударом и реакцией), нам необходимо предварительно загрузить следующую анимацию, которая будет воспроизводиться. за реакцию. Для реакций с несколькими анимациями нам нужно только предварительно загрузить одну из них, и когда она будет воспроизведена, мы сможем освободить ее и запросить потоковую передачу следующего случайного варианта. Таким образом, на каждую реакцию загружается только один вариант анимации реакции.

(Специально для режима «g_hitdeathReactions_streaming 1»): Вышеупомянутое верно только в том случае, если хотя бы один из участников, использующих профиль реакции (= реакция xml), жив. AND имеет включенный AI. AND не объединен в пул сущностей. Если ни один актер не соответствует этим требованиям, анимация реакций высвобождается из памяти.

Анимации реакций блокируются только в том случае, если профиль действителен и загружен, то есть если есть сущности, использующие его.

Заблокированы только анимации реакции. Реакции на основе графа анимации не могут заблокировать какую-либо анимацию, поскольку они не знают, какую анимацию будет запускать ввод графа анимации (поэтому эти анимации должны быть заблокированы извне).

Связанные переменные

  • g_hitDeathReactions_enable. Включает/отключает систему.
  • g_hitDeathReactions_useLuaDefaultFunctions. Если этот параметр включен, он будет использовать методы lua по умолчанию внутри сценария HitDeathReactions вместо версии C++ по умолчанию. Это не рекомендуется для целей тестирования, поскольку вызов кода lua по умолчанию (который вызывает код C++) требует больших затрат.
  • g_hitDeathReactions_disable_ai. Если этот параметр включен, он не позволит выполнять какие-либо инструкции AI во время реакции на попадание.
  • g_hitDeathReactions_debug. Если этот параметр включен, он отображает некоторую отладочную информацию поверх участников, использующих систему.
  • g_hitDeathReactions_disableRagdoll. Отключает включение тряпичной куклы в конце реакции смерти.
  • g_hitDeathReactions_logReactionAnimsOnLoading. Если эта переменная CVar включена, система будет регистрировать анимации реакций, указанные в файлах реакций. При использовании значения «1» будут записываться имена анимаций; при использовании значения «2» будут записываться пути к файлам анимации.
  • g_hitDeathReactions_streaming. Включает/отключает управление потоковой передачей для ресурсов реакции. «1» включает логику по умолчанию, которая блокирует анимацию только в том случае, если есть хотя бы один персонаж, использующий ее, который жив, с включенным AI и вне пула сущностей. «2» обеспечивает более простую логику, основанную на профиле реакции, что по сути означает, что анимации реакций блокируются всякий раз, когда существует сущность хотя бы одного из использующих их актеров.
  • g_hitDeathReactions_reload. Оперативно перезагружает всю систему: код LUA, файл определения XML и файлы данных XML.
  • g_hitDeathReactions_dumpAssetUsage. Эта команда выводит информацию об использовании ресурсов в системе в формате «загруженные активы и общее количество активов». Полезно, когда управление потоковой передачей включено для системы HitDeathReactions, чтобы иметь приблизительную оценку того, сколько памяти вы экономите.

Советы по использованию системы

  • Работая с файлом данных, начните с определения наиболее конкретных реакций и закончите наиболее общими.
  • При добавлении новой реакции протестируйте ее, поместив ее определение в начало файла данных и удалив все условия для проверки. Таким образом, эта реакция будет выбрана в 100% случаев, и вам будет проще протестировать ее выполнение. После проверки выполнения вы можете начать добавлять ограничения проверки, пока не будете уверены, что оно выбрано в ожидаемом контексте. Затем переместите его на то место в списке реакций, которое имеет смысл. Использование g_hitDeathReactions_reload команду при каждом изменении, и все будет готово через несколько минут.
  • Настраиваемые функции предназначены только для очень изолированных и специфических случаев или для быстрых тестов. Если вы часто используете настроенную функцию, то лучше перенести этот код в код C++.
  • Используйте объекты XML, чтобы избежать дублирования файлов XML. Если это поддерживается, используйте внешние объекты настолько, насколько это имеет смысл.
  • В таблице HitReactions LUA есть поле "binds" который содержит все привязки сценариев, зарегистрированные на ScriptBind_HitDeathReactions.cpp.
  • В таблице HitReactions LUA есть поле "entity" который содержит таблицу сущностей LUA связанного актера.
  • В таблице сущности LUA есть поле "hitDeathReactions" который содержит таблицу HitDeathReactions LUA этого актера.

Системные анимационные события

  • DeathReactionEnd. Немедленно завершает текущую реакцию. Для реакций на смерть это означает немедленное срабатывание тряпичной куклы, для реакций на удар это означает запуск падения и игры (если возможно). Если пользовательский параметр этого события анимации равен "спать" рэгдолл вынужден спать при срабатывании (это означает, что он замирает до тех пор, пока его не простимулирует физическая сила); на данный момент это используется только для случаев смерти от микроволновой печи.
  • RagdollStart. Завершает текущую реакцию в случайное время между запуском анимации и ее завершением. Для реакций на смерть это означает немедленное срабатывание тряпичной куклы, для реакций на удар это означает запуск падения и игры (если возможно). Если пользовательский параметр этого события анимации равен "спать" рэгдолл вынужден спать при срабатывании (это означает, что он замирает до тех пор, пока его не простимулирует физическая сила); на данный момент это используется только для случаев смерти от микроволновой печи. Если он сработает вне реакции удара/смерти, он активирует тряпичную куклу на персонаже.
  • ReactionOnCollision. Используется для анимации столкновений с реакциями окружающей среды. См. соответствующую информацию на .
  • ForbidReactions. Запрещает/Разрешает реакции. Если специальный параметр равен «0», срабатывает любая реакция. во время воспроизведения этой анимации реакции будет запрещено (когда анимация заканчивается, все возвращается в норму). Если пользовательский параметр отличается от «0», реакции будут разрешены снова.

Этот пример файла данных очень прост. Полную информацию о формате файлов данных см. .

<?xml version="1.0"?>

<!-- DTD for defining XML Internal General Entities. Think of them as macros -->
<!DOCTYPE HitDeathReactions_Example [
  <!ENTITY Legs '
    <Part value="L Leg01"/>

      <AllowedParts>
        &Legs;
      </AllowedParts>
      <AllowedHitTypes>
        <HitType value="Sniper"/>
      </AllowedHitTypes>
