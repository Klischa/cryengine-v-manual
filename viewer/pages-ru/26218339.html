Обзор

Мы постарались максимально упростить переход с WAF на CMake. В этом разделе будет описан процесс преобразования проекта.

Важные различия

Хотя мы старались сохранить максимальное сходство, есть несколько отличий, которые следует учитывать при конвертации.

  • При сборке библиотек static WAF создает список пользователей модуля, а затем собирает каждую библиотеку несколько раз, если разные пользователи модуля указывают разные флаги компиляции.
    CMake собирает каждую библиотеку static только один раз с одним набором флагов компиляции.
  • В WAF библиотеки static были встроены в объектные файлы, а затем эти объектные файлы были связаны с каждым DLL, который их использовал.
    В CMake библиотеки static проходят через промежуточный файл .a/.lib. Это может вызвать различия во время соединения.
  • Если вы используете Incredibuild для сборки, WAF ранее предоставлял вам возможность вызвать Incredibuild.
    При использовании CMake вам необходимо вызвать Incredibuild вручную.
  • Если вы включите Sandbox в свое решение, возможны только сборки отладки и профиля. Вам необходимо создать решение без Sandbox, чтобы создавать двоичные файлы выпуска.
  • CMake не предоставляет конфигурацию производительности; доступны только «Отладка», «Профиль» и «Выпуск».

Указание исходных файлов

Ключевое различие между структурой наших скриптов WAF и CMake заключается в том, что список исходных файлов встроен в один и тот же файл. CMakeLists.txt файл как расширение проекта, а не храниться во внешних файлах.

Чтобы помочь с преобразованием существующих списков файлов, мы предоставляем инструмент под названием waf2cmake, расположенный в Tools\CMake\waf2cmake.

Если вы запустите командный файл run_waf2cmake.bat, инструмент автоматически пройдет все модули WAF, определенные через Code\wscript и Engine\wscript. Если в каталоге модуля есть CMakeLists.txt, этот файл будет обновлен в соответствии со списками файлов WAF. Инструмент также может попытаться извлечь эти файлы в список изменений по умолчанию в Perforce, используя клиент командной строки Perforce.

Если у вас есть существующие игровые проекты, на которые нет ссылок ни в одном из этих файлов, вы можете использовать параметр командной строки --paths для анализа дополнительных каталогов. По умолчанию инструмент анализирует Code/GameMono, Code/GameSDK и Code/GameZero.

Версия 5.3.0 требует изменения командного файла для добавления этих параметров. В версии 5.3.1 будет добавлена ​​возможность передавать эти дополнительные аргументы непосредственно в командный файл.

Чтобы избежать случайной перезаписи важных частей файла, waf2cmake заменяет текст только между определенными, заранее определенными токенами. Если вы добавляете пользовательский модуль, который ранее был определен с помощью WAF, и хотите использовать waf2cmake чтобы заполнить список файлов, поместите следующий текст вверху вашего CMakeLists.txt перед бегом waf2cmake:

#START-FILE-LIST
#END-FILE-LIST

При запуске, waf2cmake заменит содержимое этого блока списками файлов.

waf2cmake обновляет только список исходных файлов. Настройки для отдельного проекта по-прежнему необходимо поддерживать вручную.

Преобразование проектов

В качестве примера мы будем использовать следующий модуль. Хотя это не охватывает все возможные случаи, оно должно дать достаточное представление о том, как мы выполнили эти преобразования.

  def build(bld):

    bld.CryEngineModule(
      target                  = 'MyModule',
      vs_filter               = 'CryEngine/Extensions',
      file_list               = 'mymodule.waf_files',
      win_file_list           = 'mymodule_win.waf_files',

      pch                     = 'StdAfx.cpp',
      includes                = [ Path('Code/MyModule/include'), ],
      module_provides         = dict(
        includes = [ Path('Code/MyModule/include'), ],
        defines  = [ 'MY_MODULE' ],
      ),
      use_module              = [ 'lua' ],

      win_lib                 = [ 'shell32'],
      win_x86_debug_libpath   = [ Path('Code/SDKs/MySDK/x86/debug'),
      win_x86_profile_libpath = [ Path('Code/SDKs/MySDK/x86/release'),
      win_x86_release_libpath = [ Path('Code/SDKs/MySDK/x86/release'),
      win_x64_debug_libpath   = [ Path('Code/SDKs/MySDK/x64/debug'),
      win_x64_profile_libpath = [ Path('Code/SDKs/MySDK/x64/release'),
      win_x64_release_libpath = [ Path('Code/SDKs/MySDK/x64/release'),
      win_debug_lib           = [ 'MySDKd' ],
      win_profile_lib         = [ 'MySDK' ],
      win_release_lib         = [ 'MySDK' ],
    )

Мы предполагаем, что вы уже создали пустой CMakeLists.txt файл в этом каталоге, добавил токены, упомянутые в предыдущих разделах, и запустил waf2cmake. Это автоматически позаботится о file_list и win_file_list аргументы для нас.

Начнем с объявления модуля. Это делается с помощью CryEngineModule функция, которая также позволяет нам указать предварительно скомпилированный заголовок и папку решения. Поместите это в конец файла, после #END-FILE-LIST маркер.

CryEngineModule(MyModule PCH "StdAfx.cpp" SOLUTION_FOLDER "CryEngine/Extensions")

Это автоматически подберет соответствующий список исходных файлов для вашего модуля на основе исходных файлов, перечисленных ранее в файле, вставленных пользователем. waf2cmake. Исходные файлы, которые не соответствуют вашей текущей цели сборки, будут отображаться в решении, если они доступны, но они не будут скомпилированы.

Далее мы преобразуем включения и module_provides:

target_include_directories(${THIS_PROJECT} PUBLIC ${CRYENGINE_DIR}/Code/MyModule/include)
target_compile_definitions(${THIS_PROJECT} INTERFACE -DMY_MODULE)

${THIS_PROJECT} это переменная, которая устанавливается CryEngineModule, предоставляя простой способ ссылки на модуль, определенный таким образом последним. PUBLIC и INTERFACE укажите, где применяется эта информация: PUBLIC используется для самого модуля и всего, что с ним связано, а INTERFACE применяется только к другим модулям, которые связаны с вашим модулем. Поскольку наш модуль предоставляет тот же каталог, который он использует, мы можем воспользоваться этим и прочесать их, используя PUBLIC.

Для use_module нам просто нужно подключить соответствующую библиотеку.

target_link_libraries(${THIS_PROJECT} PRIVATE lua)

В соответствии с PUBLIC и INTERFACE из предыдущей части, PRIVATE означает, что это относится только к самому модулю, а не ко всему, что связано с ним.

Далее у нас есть раздел, специфичный для Windows, поэтому нам нужно окружить следующие директивы этим блоком:

if(WIN32 OR WIN64)
  # Further directives go here
endif()

WIN32 также устанавливается в 64-разрядных сборках Windows, но его явное указание может служить напоминанием о том, что эта часть применима к обеим.

Здесь мы можем создать ссылку на Shell32 так же, как мы ранее связывались с Lua:

target_link_libraries(${THIS_PROJECT} PRIVATE shell32)

Для libpath, CMake не имеет прямого эквивалента — вместо этого вы должны указать полный путь к соответствующему модулю. Однако в некоторых случаях это может быть непросто или нежелательно, поэтому вы все равно можете эмулировать эту директиву. Нам нужны разные папки для каждой платформы, поэтому мы отделим общие части и добавим часть, специфичную для платформы, отдельно:

set(MySDK_basedir ${SDK_DIR}/MySDK)
if (WIN64)
  set(MySDK_dir ${MySDK_basedir}/x64)
elseif(WIN32)
  set(MySDK_dir ${MySDK_basedir}/x86)
endif()
set_libpath_flag()
set_property(TARGET ${THIS_PROJECT} APPEND_STRING PROPERTY LINK_FLAGS_DEBUG " ${LIBPATH_FLAG}${MySDK_dir}/debug")
set_property(TARGET ${THIS_PROJECT} APPEND_STRING PROPERTY LINK_FLAGS_PROFILE " ${LIBPATH_FLAG}${MySDK_dir}/release")
set_property(TARGET ${THIS_PROJECT} APPEND_STRING PROPERTY LINK_FLAGS_RELEASE " ${LIBPATH_FLAG}${MySDK_dir}/release")

Пробел после открывающей кавычки необходим для обеспечения корректной работы.

Наконец, нам нужно указать ссылку на MySDK. Для этого мы используем выражения-генераторы CMake. В этом случае мы будем использовать одно выражение для соответствия нашей библиотеке только для отладки, а другое — для соответствия другим конфигурациям:

target_link_libraries(${THIS_PROJECT} PRIVATE $<$<CONFIG:Debug>:MySDKd> $<$<NOT:$<CONFIG:Debug>>:MySDK>)

При связывании нескольких библиотек с определенной конфигурацией каждая библиотека должна иметь собственное выражение-генератор. Пробелы в выражениях генератора могут работать ненадёжно.

На этом преобразование модуля завершено. Последний шаг — заставить CMake включить модуль. Для этого мы идем в Tools\CMake и добавьте соответствие add_subdirectory директиву соответствующему Build*.cmake файл. Так как это модуль двигателя, открываем BuildEngine.cmake и добавьте следующую строку в нужное место:

add_subdirectory ("${CRYENGINE_DIR}/Code/MyModule" "${CMAKE_BINARY_DIR}/MyModule")
