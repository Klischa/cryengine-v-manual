Пример плагина

Чтобы упростить создание нового плагина и продемонстрировать некоторые его функции, мы создали SamplePlugin. Вы можете найти код для SamplePlugin в Код/Sandbox/Плагины/SamplePlugin.

Если вы хотите протестировать образец плагина самостоятельно, используйте опцию CMake. OPTION_SAMPLEPLUGIN при создании вашего решения.

Создание нового плагина

  • Создайте новую папку для размещения вашего плагина.
  • Первый метод: скопируйте SamplePlugin
    • Сохраните следующие файлы:
      • SamplePlugin.h
      • SamplePlugin.cpp
      • StdAfx.h
      • StdAfx.cpp
      • CMakeLists.txt
    • При необходимости переименуйте файл и его содержимое.
    • Удалите демонстрационные файлы, поскольку они не нужны, или сохраните их в качестве примера.
  • Второй метод: с нуля
    • Создайте к нему файл CMakeLists.txt по образцу других проектов. См. зависимости ниже, чтобы убедиться, что вы используете только то, что подходит для плагина редактора.
    • Мы рекомендуем вам следовать структуре папок образца плагина, который содержит предварительно скомпилированный заголовок и отдельный файл заголовка/cpp для плагина. Однако вы можете написать код в любой файл. Регистрация плагина выглядит так:
class CSamplePlugin : public IPlugin
{
public:
  CSamplePlugin() { /* entry point of the plugin, perform initializations */ }
  ~CSamplePlugin() { /* exit point of the plugin, perform cleanup */ }
  int32       GetPluginVersion() { return 1; };
  const char* GetPluginName() { return "Sample Plugin"; };
  const char* GetPluginDescription() { return "Some description of your plugin"; };
private:
};
 
//Macro to register the plugin
REGISTER_PLUGIN(CSamplePlugin);

Зависимости пакета

  • Плагины всегда должны зависеть от EditorInterface и EditorCommon.
  • Плагины, конечно, могут зависеть от пакетов и модулей движка.
  • Плагины редактора также могут зависеть друг от друга.
  • Компоненты многократного использования следует размещать в EditorCommon, делиться результатами своей работы, не хранить их в коде плагина.
  • Не добавляйте зависимость от MFCToolsPlugin, MFC или Windows SDK. Насколько это возможно, ваш плагин должен быть независимым от платформы. Существует несколько вариантов аппаратной абстракции от CryEngine API и Qt API, которые должны удовлетворить ваши потребности.
  • Не добавляйте зависимость от Sandbox, даже если кажется, что она вам нужна. Если вам нужны какие-то вещи из Sandbox, которые не были раскрыты, вы должны раскрыть их одним из этих методов:
    • Добавьте в EditorInterface интерфейс, реализованный в Sandbox. Таким образом, вы предоставили некоторую функциональность, не привязывая свой плагин к реализации в Sandbox, которая, скорее всего, изменится. Для этого потребуется запрос на включение, который будет принят командой движка.
    • Переместите классы в EditorCommon, но только в том случае, если они предназначены для многократного использования, и постарайтесь избежать слишком большого количества зависимостей. Для этого потребуется запрос на включение, который будет принят командой движка.
    • Не рекомендуется: добавьте новые методы в IEditor. Это действительно актуально только при предоставлении «глобального» типа функциональности, поскольку все новые концепции следует добавлять в отдельные интерфейсы, чтобы не раздувать IEditor и сохранять модульную архитектуру редактора.
    • Помните, что код Sandbox все еще претерпевает серьезные изменения, и его следует рассматривать как «черный ящик».

Что вы можете сделать с помощью плагина

  • Добавьте новые инструменты и закрепляемые окна.
  • Добавить команды
  • Добавить страницы настроек
  • Добавить виджеты в трее
  • Регистрация новых типов активов
  • Зарегистрируйте новые типы объектов для размещения на уровне.
