Обзор

Миграция хоста — это процесс передачи владения игрой от одного хоста к другому. Это может произойти разными способами, которые в целом можно разделить на три категории:

  1. Миграция лобби: текущий хост определяет, что клиент в лобби является более подходящим кандидатом, прежде чем начать игру.
  2. Контролируемая миграция: текущий хост выходит из игры контролируемым образом, т.е. через внутриигровое меню.
  3. Катастрофическая миграция: текущий хост теряет соединение с Интернетом, выходит из строя или отключается электропитание.

CRYENGINE обрабатывает все три случая с определенной степенью контроля со стороны программиста. Кроме того, процесс миграции хоста контролируется, поэтому, если новый хост выйдет из строя, выйдет из строя или потеряет питание, выбирается другой хост до тех пор, пока в игре больше не останется клиентов или не будет достигнут лимит времени миграции хоста (известный как событие множественной миграции).

Миграция хоста осуществляется на основе сеанса

Миграция хоста основана на сеансах, и каждый сеанс может мигрировать независимо (и одновременно). Сеансы необходимо создавать как переносимые (или нет), предоставив CRYSESSION_CREATE_FLAG_MIGRATABLE пометить ICryMatchMaking::SessionCreate().

Миграция хоста — это услуга лобби

Это также контролируемая функция службы лобби; индивидуальную службу лобби можно настроить для нет поддержка миграции хоста (по умолчанию поддерживается через eCLSF_SupportHostMigration флаг), чтобы игра могла поддерживать миграцию хоста только на выбранных платформах, если это необходимо (например, миграция хоста имеет смысл только в одноранговой среде; если одна платформа использует выделенные серверы, то можно запретить миграцию сеансов). В службу лобби можно запросить поддержку миграции хоста следующим образом:

bool hostMigrationSupported = gEnv->pNetwork->GetLobby()->GetLobbyServiceFlag(<lobby_service_type>, eCLSF_SupportHostMigration);

где <lobby_service_type> — это eCLS_LAN или eCLS_Online.

Определение нового хоста

Выбор «лучшего» хоста определяется подсказками, которые синхронизируются между всеми клиентами в игре. Критерии определения лучшего хостера следующие:

  1. Тип NAT (открытый лучше умеренного, который лучше строгого, причем неизвестные NAT считаются худшими).
  2. Количество активных одноранговых подключений для этого клиента (больше подключений означает, что на новый хост можно «перетянуть» больше клиентов).
  3. В случае, если два клиента считаются равными по типу NAT и количеству подключений, используется уникальный идентификатор сетевого канала. Это сделано исключительно для того, чтобы навязать всем клиентам полностью детерминированную эвристику.

Список подсказок поддерживается текущим хостом в течение long, пока сеанс активен (и поддерживает миграцию хоста), и распространяется на все клиенты.

Переменные консоли миграции хоста

Существует ряд переменных консоли, которые можно использовать как для управления миграцией хостов, так и для отображения информации о списке подсказок и состоянии каждой машины:

  • net_migrate_timeout — это общее время, отведенное для завершения событий миграции (по умолчанию — 30 секунд). Все миграции должны произойти для сеанса в течение этого периода времени, иначе миграция хоста будет прекращена.
  • net_automigrate_host - переключает, будет ли выполняться автоматическая миграция при потере соединения с хостом (по умолчанию 1 = включено). Это можно использовать для защиты разделов кода, когда вы не хотите, чтобы происходила миграция хоста, но вы все равно хотите, чтобы эта возможность поддерживалась.
  • net_show_host_identificiation - переключает отображение идентификации хоста на экране (по умолчанию 0 = выключено). Это показывает статус любого конкретного компьютера во всех участвующих в нем сеансах и отображает либо «HOST», «ANTICIPATED NEW HOST» или «MEMBER».
  • net_show_new_host_hinting - переключает, отображается ли список подсказок хоста на экране (по умолчанию 0 = выключено). Это показывает список подсказок любой конкретной машины во всех ее участвующих сеансах. Хост будет иметь подсказку для каждого клиента в игре (за исключением себя), а каждый клиент будет иметь подсказку для каждого однорангового клиента (за исключением себя и хоста). Таким образом, в полностью связанной игре с четырьмя участниками хост увидит три подсказки (по одной для каждого клиента), а каждый клиент увидит по две подсказки (по одной для каждого клиента, исключая хоста).
  • net_hostHintingNATTypeOverride - переопределяет указанный тип NAT (по умолчанию 0 = выключено; 1 = открыто, 2 = умеренно, 3 = строго, 255 = неизвестно). Эта команда полезна для создания или повторения тестовых ситуаций. Очевидно, что на самом деле он не меняет тип NAT, а только то, что сообщается в подсказке, и используется для того, чтобы гарантировать, что конкретная машина либо исключена в качестве кандидата на хост (путем сообщения о более строгом типе NAT), либо выбрана предпочтительно (путем сообщения о более открытом типе NAT).
  • net_hostHintingActiveConnectionsOverride - переопределяет сообщаемое количество активных соединений (по умолчанию 0 = выключено). Эта команда полезна для создания или повторения тестовых ситуаций. Очевидно, что на самом деле это не меняет количество активных подключений, а только то, что сообщается в подсказке, и используется для того, чтобы гарантировать, что конкретная машина либо исключена из числа кандидатов на хост (сообщив о меньшем количестве подключений), либо выбрана в качестве предпочтительного (сообщив о большем количестве подключений; до 255).

Процесс миграции хоста

Процесс миграции хоста проходит ряд этапов, и на каждом этапе необходимо выполнить определенные действия. Чтобы облегчить это, классы могут регистрировать интерес к событиям миграции хоста с помощью шаблона интерфейса прослушивателя.

Во-первых, ваш класс должен наследовать от IHostMigrationEventListener (определенного в INetwork.h):

struct IHostMigrationEventListener
{
  virtual void OnInitiate(SHostMigrationInfo& hostMigrationInfo, uint32& state) = 0;
  virtual void OnDisconnectClient(SHostMigrationInfo& hostMigrationInfo, uint32& state) = 0;
  virtual void OnDemoteToClient(SHostMigrationInfo& hostMigrationInfo, uint32& state) = 0;
  virtual void OnPromoteToServer(SHostMigrationInfo& hostMigrationInfo, uint32& state) = 0;
  virtual void OnReconnectClient(SHostMigrationInfo& hostMigrationInfo, uint32& state) = 0;
  virtual void OnFinalise(SHostMigrationInfo& hostMigrationInfo, uint32& state) = 0;
  virtual void OnTerminate(SHostMigrationInfo& hostMigrationInfo, uint32& state) = 0;
  virtual void OnReset(SHostMigrationInfo& hostMigrationInfo, uint32& state) = 0;
};

Во-вторых, ваш класс должен зарегистрироваться на сетевом уровне. Лучше всего это сделать в конструкторе класса с помощью следующего:

gEnv->pNetwork->AddHostMigrationEventListener(this, "<your_class_name>");

где <your_class_name> — это просто текстовая строка, используемая для облегчения прослушивания отладки.

Соответствующий вызов для отмены регистрации вашего класса должен идти в его деструкторе:

gEnv->pNetwork->RemoveHostMigrationEventListener(this);

После регистрации ваш класс будет иметь методы, определенные в IHostMigrationEventListener, вызываемые во время события миграции хоста. Каждый метод принимает два параметра (предоставляемых сетевым уровнем), а именно ссылку на структуру SHostMigrationInfo, которая содержит информацию об этом событии миграции хоста, и ссылку на внутреннее состояние прослушивателя (см. ниже). Методы вызываются в том порядке, в котором они объявлены в интерфейсе:

  • OnInitiate() вызывается в начале события миграции хоста. Этот метод отвечает за хранение любой соответствующей информации, необходимой для сохранения во время миграции (например, инвентаря игроков).
  • OnDisconnectClient() вызывается, когда клиент отключается от исходного хоста. Вполне возможно, что этот метод будет вызван на старом хосте (в случае миграции лобби).
  • OnDemoteToClient() вызывается у каждого клиента, который нет новый хост - это означает, что у клиентов, оставшихся клиентами, будет вызываться этот метод. Вполне возможно, что старый хост вызовет этот метод (в случае миграции лобби), поскольку ему, возможно, придется скорректировать внутреннее состояние, чтобы стать клиентом.
  • OnPromoteToServer() называется только о предполагаемом новом ведущем сессии.
  • OnReconnectClient() вызывается для всех клиентов, независимо от того, были ли они старым хостом, новым хостом или остались клиентом.
  • OnFinalise() вызывается на всех клиентах, будь то старый хост, новый хост или оставшийся клиент. Это используется для освобождения временных ресурсов, которые могли быть выделены в OnInitialise().
  • OnTerminate() вызывается в случае ошибки (которая может произойти на любом этапе процесса миграции хоста, поэтому убедитесь, что любая очистка, выполненная в OnFinalise(), также выполняется здесь).
  • OnReset() вызывается, когда ожидаемый новый хост покидает часть процесса миграции хоста. Обратите внимание, что после этого метода внутренний конечный автомат миграции хоста вернется к OnDisconnectClient(), нет OnInitiate().

Каждый метод возвращает логическое значение, с правда что означает «вся обработка на этом этапе завершена», и ложный что означает «требуется дополнительная обработка». Только когда все зарегистрированные прослушиватели для данного состояния вернутся. правда переходит ли процесс миграции хоста в следующее состояние. Это позволяет асинхронным задачам, таким как отключение или повторное подключение, полностью завершиться перед переходом в следующее состояние (переданная ссылка 'государство' гарантированно будет равен 0 при первом вызове прослушивателя и сохранит свое значение при последующих вызовах до тех пор, пока прослушиватель не завершится - полезно для управления конечными автоматами на основе переключателей).

Ответственность игры за миграцию хоста

CRYENGINE выполняет большую часть работы, необходимой для переноса сеанса на новый хост, но игра будет иметь некоторые обязанности.

Во-первых, после подключения клиента к хосту существует период времени, когда вновь подключенному клиенту просто не хватает информации, чтобы взять на себя обязанности хоста, если хост выйдет из строя или выйдет из строя. Чтобы смягчить это, все клиенты изначально сообщают, что они не подходят в качестве хоста любого сеанса, к которому они подключаются, путем сообщения нежелательной подсказки хоста текущему хосту. Как только игра посчитает, что у клиента достаточно информации, чтобы взять на себя ответственность за хостинг сеанса, игра должна как минимум сделать следующее:

ICryMatchMaking* pMatchMaking = gEnv->pNetwork->GetLobby()->GetLobbyService()->GetMatchMaking();
pMatchMaking->SessionSetLocalFlags(<game_session_handle>, CRYSESSION_LOCAL_FLAG_HOST_MIGRATION_CAN_BE_HOST, NULL, NULL, NULL);

где <game_session_handle> — дескриптор сеанса, который был возвращен в обратном вызове из SessionCreate(). Параметры NULL в примере кода являются обычными параметрами обратного вызова лобби/матчмейкинга, а именно аргументами обратного вызова CryLobbyTaskID*, CryMatchmakingFlagsCallback и void*, и здесь для краткости опущены. Важно отметить, что это необходимо сделать для каждого сеанса, которым управляет игра и желает, чтобы этот клиент считался хостом, если инициируется событие миграции хоста.

Во время события миграции для текущей игры клиенты выполняют несколько задач по установлению контекста, которые необходимы при подключении к новому серверу, однако они пропускают этапы демонтажа. Поэтому игра должна решить, что больше не нужно, и выбросить это по мере необходимости. Это следует сделать путем создания списка объектов, которые больше не будут нужны после миграции в OnDemoteToClient() прослушиватель, а затем удалив их в OnFinalise() слушатель. Обратите внимание, что в случае события миграции клиент может начать миграцию на новый хост (оставшись клиентом), но этот хост уйдет (контролируемым или катастрофическим образом), и этот клиент впоследствии станет хостом (событие множественной миграции). Это важный момент, который следует помнить, поскольку это означает, что во время события многократной миграции список объектов, созданных в OnDemoteToClient() слушатель не должен быть удалены до тех пор, пока OnFinalise() прослушиватель (это момент, когда миграция хоста по существу завершена), в противном случае клиент, который становится хостом, не будет знать об объектах, над которыми он должен взять на себя контроль. Это также означает, что список сущностей на любом клиенте, который остается клиентом во время события многократной миграции, может содержать повторяющиеся записи, поскольку OnDemoteToClient() прослушиватель будет вызываться более одного раза. В этой ситуации можно безопасно немедленно удалить дубликаты.

Игра также отвечает за то, чтобы повторно подключающимся клиентам был назначен правильный актер. Это делается внутри CGameRules::SetChannelForMigratingPlayer() и CGameRules::OnClientConnect():

  • SetChannelForMigratingPlayer() должен вернуть EntityId что соответствует актеру, назначенному этому каналу.
  • OnClientConnect() обычно отвечает за создание актера для нового клиента, но в случае миграции хоста ему необходимо использовать кэшированный EntityId из SetChannelForMigratingPlayer(), поскольку эта сущность-актёр уже существует.

Во время события миграции на Xbox LIVE SessionID изменено, и это приведет к .m_SID компонент SConnectionUID чтобы все соединения в вестибюле были изменены. Чтобы сопоставить обновление со связанным с ним игроком, SConnectionUIDследует использовать только .m_UID компонент для целей сравнения.
