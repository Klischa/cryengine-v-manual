Обзор

Сеть в движке стала возможной благодаря CryNetwork модуль и доступен сущностям через INetEntity интерфейс - доступен через IEntity::GetNetEntity. Объекты по умолчанию не подключены к сети, но могут быть привязаны к сети во время создания — если компонент вызывает INetEntity::BindToNetwork раньше IEntitySystem::InitEntity вызывается на сущность.

После привязки к сети объектам присваивается идентификатор сетевого объекта (SNetObjectID), который используется для уникальной идентификации объекта в сети.

Идентификаторы объектов нет гарантированно будет одинаковым по сети и, следовательно, не может быть отправлен без преобразования. См. Политики сжатия раздел ниже.

Каналы

Канал представляет собой соединение с другим экземпляром механизма и известен в коде как INetChannel. По умолчанию сервер имеет один сетевой канал на каждого клиента, и каждый клиент имеет один сетевой канал для связи с сервером.

Каждый канал имеет уникальный идентификатор, который используется для идентификации соединения и обычно используется во время соединений, например, для идентификации игрока на сервере. Однако имейте в виду, что идентификатор канала не подключен к сети, поэтому его не следует сериализовать по сети, как идентификаторы объектов.

Политики сжатия

Все сетевые данные сериализуются через ISerialize построить, в частности, с помощью функции ISerialize::Value. Очень важным аспектом этой функции является возможность предоставить необязательный третий параметр для указания политика сжатия. Политики сжатия позволяют указывать размер и диапазоны данных, передаваемых по сети, гарантируя, что используемая полоса пропускания будет как можно ниже.

Политики сжатия по умолчанию можно увидеть в Двигатель/Конфигурация/DefaultScripts/CompressionPolicy.xml. Например, 'ид' политика используется для автоматического преобразования идентификаторов объектов в сетях в их удаленные эквиваленты. Это полезно, поскольку идентификаторы сущностей не обязательно будут одинаковыми в разных экземплярах игры. Например:

ser.Value("myEntityId", myEntityId, 'eid');

Это позволит при записи прочитать значение 'myEntityId' и найти его внутреннее значение. SNetObjectID и сериализовать его по сети. Принимающий экземпляр движка затем десериализует локальный эквивалент в «myEntityId», гарантируя, что мы ссылаемся на один и тот же экземпляр объекта на разных машинах.

Ознакомьтесь с различными доступными политиками сжатия: сжатие данных по сети может иметь решающее значение для поддержания использования полосы пропускания клиента и сервера на устойчивом уровне. Также можно добавить собственные политики или override политики по умолчанию, добавив Скрипты/Сеть/CompressionPolicy.xml файл в каталог ваших ресурсов. Затем мы можем использовать тот же формат, что и по умолчанию XML, упомянутый выше.

Рекомендуется использовать политики сжатия с самого начала написания сетевого кода. Всегда будет проще заранее подумать об использовании, чем анализировать всю базу кода для оптимизации пропускной способности позже, во время производства.

Удаленные вызовы методов

Удаленные вызовы методов (RMI) позволяют удаленно выполнять функции между клиентом и сервером. Обратите внимание, что RMI могут нет использоваться для связи между несколькими клиентами. В коде они представлены СРми структура. Каждый удаленный метод может содержать набор параметров, которые необходимо сериализовать одним и тем же способом. Сетевая сериализация и аспекты

Каждый сетевой объект может сериализовать данные по сети всякий раз, когда определенный аспект (см. EEntityAspects) изменено. Например, предположим, что у нас есть логическое значение с именем m_bWalking, мы могли бы сериализовать это по сети, чтобы убедиться, что все клиенты и сервер знают текущее состояние синхронизации. Каждая сущность может иметь до 32 аспектов, которые сериализуются независимо всякий раз, когда код игры помечает ее как «грязную».

При использовании всех аспектов нет никаких накладных расходов, часто бывает полезно разделить сериализацию на несколько аспектов, чтобы уменьшить использование полосы пропускания.

Рекомендуется группировать переменные по аспектам на основе скорости изменения, поскольку их потребуется сериализовать одновременно. Например, положение и вращение обычно сериализуются вместе, тогда как здоровье не зависит.

При обработке сериализованных данных нам сначала нужно выбрать уникальный аспект, с которым мы хотим передавать данные. Например, предположив, что мы хотим сериализовать данные от клиентов на сервер и других клиентов, мы могли бы выбрать eEA_GameClientD. Каждый раз, когда данные, которые мы в последний раз отправляли по сети, изменяются, нам нужно будет позвонить IGameObject::ChangedNetworkState, фактически отмечая аспект как грязный, что приводит к IEntity::NetSerialize вызывается для чтения данных.

История аспектов и дельты

Самым большим преимуществом аспектов по сравнению с RMI является встроенная обработка истории аспектов. Это означает, что и сервер, и клиент будут помнить, что в последний раз было отправлено на удаленную сторону, что позволяет нам использовать дельта-сжатие для отправки в сеть только измененных данных — вместо того, чтобы требовать полного обновления каждого аспекта каждый раз, когда он помечен как «грязный».

Это эффективный инструмент для оптимизации использования полосы пропускания, и на него следует полагаться как можно больше. Имейте в виду, что вызов десериализации всегда будет override данных с тем, что было на сервере, даже если использовалось дельта-сжатие для уменьшения объема, который необходимо было отправить. Это означает, что недоверенный клиент не может свободно изменять сериализованные значения без потенциального переопределения при десериализации.

Делегирование аспектов

Обычно (и по умолчанию) сущности контролируются сервером. Однако в некоторых случаях необходимо делегировать управление аспектом клиенту. Обычно это делается для улучшения реакции клиента, но требует доверия к клиенту, что может привести к относительной легкости разработки читов.

Чтобы включить делегирование определенного аспекта сущности, нам сначала нужно вызвать INetEntity::EnableDelegatableAspect: Затем мы можем позвонить INetContext::DelegateAuthority.

Сериализация репликации спауна

Часто бывает полезно сериализовать данные об объекте во время создания. Это используется для создания объекта с предопределенными компонентами и данными на стороне сервера и автоматической десериализации этого конкретного набора данных, когда объект создается на удаленном клиенте(ах).

Это достигается путем переопределения IEntityComponent::NetReplicateSerialize функцию и прикрепление компонентов к объекту до вызова IEntitySystem::Init.
